# Upstream reachability is observed, not enforced

ADR-0002 splits every feature into core (fail-fast) and side (degrade + warn), and ADR-0004 confines format-coupled guards to Standard Mode. Both operate on the **rendered config**, which is the right layer and also the limit: `upstreams_default_has_resolver` proves a resolver is *present*, never that it *answers*. A pinned resolver that has gone dark passes it exactly like one that replies.

Nothing downstream noticed either (#310). `init_strategy: blocking` logs upstream errors and keeps running; the Supervisor watchdog polls `/api/blocking/status`, which reports blocking state and answers 200 with no working resolver; and denylists download over the host's own resolver path, so list loading succeeds while resolution is dead. Total resolver death therefore started clean, stayed green, and reached the operator only as client-side timeouts. Since ADR-0011 freezes the three shipped resolvers into every install that has ever pressed Save, the values cannot be corrected — which makes the *invisibility*, not the values, the defect.

**Decision: this is an observability gap and gets an observability fix.** A long-running service (`etc/services.d/upstream-probe`) asks the running Blocky to resolve a name every 5 minutes and reports the verdict in the add-on log: a warning after two consecutive failures, repeated after every twelve further failed probes, and an info line on recovery. It never aborts the add-on, never restarts Blocky, and never touches the config.

What it watches is precisely the group that serves a local client — the `default` group in the shipped config, which is the frozen set #310 is about. A per-client group that no local query reaches is out of its view.

Four properties make the probe's verdict trustworthy, and each is a correctness requirement rather than a detail:

- **The query name is random and under a nonexistent TLD** (`p<random>.blocky-addon-probe`). A fixed name would be answered from Blocky's cache on the second probe onward, and a cache hit proves nothing about upstreams. A nonexistent TLD is answered NXDOMAIN by the root servers, so the probe reaches no third party's zone; two labels keep `fqdn_only` from rejecting it locally; and the suffix is self-identifying for an operator who finds it in their query log.
- **Only `RESOLVED` counts as proof.** Everything Blocky can answer by itself — cache, blocking, filtering, custom DNS, hosts file, special-use names — is classified *inconclusive* and never warns, because it says nothing about upstreams. So is an unrecognised response type, so a future Blocky vocabulary change degrades to silence rather than to a false verdict. `CONDITIONAL` looks like a second healthy case and is deliberately excluded: a conditional mapping that swallowed the probe name would prove a *conditional* upstream is alive while saying nothing about the default group.
- **"Blocky is not answering" is not an upstream verdict, but "Blocky accepted the query and never answered" is.** Both arrive as the same absent HTTP status, so the status alone cannot separate them and curl's exit code does: a refused or otherwise failed connection is *inconclusive* and stays quiet, because Blocky is down or still starting and Blocky's own logging owns that failure. A timeout (curl 28) classifies as *failed* and warns. Against a listener on `127.0.0.1` a connection either succeeds or is refused at once, so a timeout there means the query was accepted and the resolver chain hung — which is exactly what an upstream that drops packets instead of refusing them looks like, and staying quiet on it would restore the silence this probe exists to break. The probe therefore imposes its own budget (30s) rather than waiting out `upstreams.timeout`, which an operator may set arbitrarily high: a lookup no stub resolver on the network would wait for is a failure from every client's point of view, whatever the config says.
- **There are three verdicts, not four, because there are three behaviours.** An earlier draft split the quiet bucket into *inconclusive* (Blocky answered locally) and *unreachable* (Blocky did not answer at all). The distinction reads well and is behaviourally empty: both land in the same branch of the loop and do the same nothing. Two names for one state is a taxonomy that has to be maintained and explained without ever being consulted, so the quiet bucket is one verdict. The *reason* it is quiet still varies, and that belongs in the comment where the branch is taken, not in the return value.
- **"Consecutive" means consecutive.** Any non-failure verdict, including an inconclusive one, resets the failure run. Without that, one failure today and one next week would eventually add up to a warning about an outage that never happened.

**Standard Mode only**, for ADR-0004's reason applied to a different surface: the probe's fixed `127.0.0.1:4000` is a fact of the config *we render*. In Custom Config Mode the operator decides whether there is an HTTP listener at all and on which port, so probing it would report their deliberate choice as a failure.

**Considered & rejected.**

1. *Point the watchdog at something truthful.* The most attractive option on paper — the Supervisor already polls it, so an unhealthy add-on would appear in the UI without anyone reading a log. It is not implementable and would be wrong if it were. Blocky v0.34 exposes no endpoint reflecting upstream health: `/api/blocking/status` reports blocking, `/api/stats` needs statistics enabled and reports a rolling window, and `/api/query` — the only endpoint that actually resolves — is a POST, which the watchdog cannot issue. Serving our own health endpoint for the watchdog to poll would close that gap and open a worse one: an unhealthy watchdog makes the Supervisor **restart the add-on**, so a transient upstream outage would become a restart loop that takes DNS down for the whole network rather than reporting it.
2. *Ship `init_strategy: failOnError`.* Loud, and wrong for the same reason: it trades a silent failure for a refusal to boot during an outage the add-on cannot fix. It is also an Operator-owned default (ADR-0011), so it would reach new installs only — the installs that do not have the problem.
3. *A one-shot probe at startup.* Cheaper, and it answers the question the sweep asked. But resolvers die months after a boot, and a check that only runs at start is silent for exactly the case that motivated this. The loop costs one query per 5 minutes.
4. *Fail fast when the probe fails.* Rejected on ADR-0002's own terms: its core/fail-fast rule is written for configs *structurally* incapable of resolving, which a guard can prove from the rendered file. A resolver that is down now may answer in a minute, and no amount of aborting makes it answer sooner.
5. *Do nothing, document it.* The residual risk is smaller than the resolver count suggests (two vendors, not three — ADR-0011), but "document it" puts the explanation in a page read before the outage, while the probe puts it in the log the operator opens *during* one.

**Consequences.**

- **The signal still lives only in the log**, which is the very complaint #310 raised about Blocky's own line ("a log line they have no reason to be reading"). This is accepted rather than solved, because the add-on has no other honest surface: the only Supervisor-visible state is the watchdog, and the watchdog's response to bad news is to restart the add-on (rejection 1). What changes is what the log *says* — an operator who opens it during an outage now finds a sentence naming the cause and the setting to check, instead of one upstream error among the startup noise. If Home Assistant ever gives add-ons a non-restarting way to report degraded state, that is the follow-up.
- The probe adds one DNS query per 5 minutes to the upstreams — 288 a day, permanently — and each appears in the query log and in `/api/stats` as an NXDOMAIN. That is the price of the signal and is documented in DOCS.md so it is not mistaken for stray traffic.
- The verdict logic (`usr/lib/blocky/upstream_probe.sh`) is pure and pinned by `scripts/test-guards.sh` against recorded API responses, so the classification is tested without a network — but the loop itself, like `services.d/blocky/run`, is only exercised end-to-end by hand.
- The probe is coupled to the `/api/query` response shape *and* to how Blocky behaves when it cannot answer — a 5xx, a SERVFAIL body, or holding the connection open, the last of which is read through curl's exit code rather than through anything Blocky sends. Both join the rendered-config format as things a Blocky bump must be re-checked against (ADR-0009); `docs/agents/blocky-bump-review.md` carries the consumed API surface as a second scan surface, since the render harness validates YAML and can never see it. An unrecognised *shape* reads as inconclusive, so that failure mode is a probe that stops reporting rather than one that lies; a change in *hanging* behaviour is the one that could make it lie, which is why the bump review holds on it.
- The gap this closes is *detection only*. Nothing about it makes the frozen resolver values correctable; ADR-0011's heavy lever is still the only way to change them for existing installs.
