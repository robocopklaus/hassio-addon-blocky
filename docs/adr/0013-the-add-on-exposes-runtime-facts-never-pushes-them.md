# The add-on exposes runtime facts, never pushes them

ADR-0012 gave the add-on a probe that knows whether the configured upstreams still answer, and then had to accept that the verdict lives only in the log — "the add-on has no other honest surface". That ADR named its own follow-up: *if Home Assistant ever gives add-ons a non-restarting way to report degraded state, that is the follow-up.* This is it, asked more generally: **should this add-on publish Home Assistant entities at all** — for upstream reachability, and for blocking control, whose `rest_command` recipe already ships in `DOCS.md`.

The question is not academic. #318 verified that Blocky v0.34.0 exposes **no GET-able upstream-health signal**: `/api/blocking/status` reports blocking and answers 200 with a dead resolver, `/api/stats` needs statistics enabled, and `/api/query` — the only endpoint that resolves — is a POST. So an HA-native `rest` sensor pointed at `:4000` can report blocking and can never report resolution. The probe is the only thing that knows, and #326 found its verdict is not merely log-only but **edges-only**: three shell locals and transition-only log lines, where silence is the healthy signal and is indistinguishable from a dead probe.

## The direction rule

**Decision: the add-on exposes, others consume.** It never holds an outward connection, never runs a second process to maintain one, and never owns state in another system's registry. Entities are Home Assistant's to create and own; publishing them is outside this add-on's role.

The strict reading of that — *translation layer, nothing more, the probe stays log-only* — is rejected too, because it fails by construction: it would produce a `DOCS.md` recipe for a signal that does not exist, leaving the motivating need unanswerable. So the domain widens by exactly one step: **the add-on is obliged to make its own runtime facts readable, and its obligation ends there.** That is still "options in, artifacts out" — one more artifact alongside the Rendered config — with no broker, no credentials, no second runtime process, and no state held elsewhere. `CONTEXT.md` carries **Runtime fact** as a Language entry.

This is recorded as a **general direction rule**, not a ruling about entities, and it plays the role for runtime surfaces that ADR-0006 plays for the configuration surface: the next "make the add-on talk to X" — MQTT, webhooks, notifications, push to anything — is answered here rather than re-litigated per request. The cost is accepted knowingly: the rule binds cases not yet imagined, and re-opening it means a new ADR.

Four arguments carry it. **Proportionality** — the payload is essentially one boolean, and a permanent broker dependency with credential handling, availability topics and retained-state staleness is out of proportion to it. **A broker cannot be assumed** — HA's MQTT integration is optional, so the non-broker path needs documenting regardless, i.e. two maintained paths instead of one. **It matches the ecosystem** — #324 found AdGuard and Pi-hole both putting entity publishing in a *core integration* that polls, with the add-on only declaring `discovery:`; the add-on is not where entities come from. **It keeps the door open** — a future integration consumes the same readable surface, where choosing push would have pre-committed the transport.

Reach — "how many users even run a broker" — was rejected as a primary criterion, since this repo has no telemetry to measure it, and admitted only as an argument inside the cost weighing above.

## The surface

**Decision: the add-on serves its own read-only HTTP status endpoint**, on a new published port, carrying the probe's verdict as a small JSON document the probe writes atomically. The operator adds one `rest` sensor — the exact mirror of the `rest_command` block `DOCS.md` already ships.

Core-readability is a **hard requirement**, not a preference: the one step of widening exists precisely so a consumer can reach the fact, and a surface HA core cannot read leaves the need unmet while looking like a yes. That requirement decided it. It kills a `/config` status file outright — HA core cannot read `/addon_configs/<slug>/`, the reordering fact #326 turned up, since the already-mounted path is *not* the cheap option it appears to be — and a `/data` file with it. Against the survivors, an own endpoint uniquely gets **honest availability for free**: add-on down → connection refused → the sensor reads `unavailable`. That is the property #325 found MQTT retained state cannot give and a status file cannot give either, and it is worth more than it costs, because a health sensor that lies while stopped is worse than no sensor.

It is also cheaper than it first looked. `busybox httpd` is absent from the base image, but `darkhttpd` is a 19.4 K Alpine package — a 43 KB static binary with no config file — so the cost is one `apk add`, a ~5-line s6 service, and one `ports:` / `ports_description:` entry on the curated surface. Two facts blunt the exposure objection: `:4000` already ships as an unauthenticated LAN listener that can *mutate* blocking state, so a read-only status endpoint is strictly less exposure than what already ships; and the direction rule governs *outward* connections, so a passive listener sits near the line rather than over it.

Four semantics are part of the decision, not implementation detail:

- **The listener runs in both configuration modes**, answering `disabled` in Custom Config Mode. ADR-0004 binds only guards that *text-parse* the rendered config; this endpoint parses nothing, so the Standard-Mode gate does not reach it. Parking it with the probe would leave the sensor permanently `unavailable`, conflating "you chose Custom Config Mode" with "the add-on is stopped".
- **`state` is derived honestly, not mirrored** — `healthy` / `failing` / `unknown` / `disabled`, with the raw last-probe outcome and a timestamp alongside. When the last probe was inconclusive, the endpoint reports **`unknown`**, not the frozen level. This is a **deliberate divergence from ADR-0012's rationale**: that ADR defends the freeze on the grounds that "Blocky's own logging owns that failure", which is sound for a human reading a log with Blocky's errors on the same screen and does not survive the move to a machine consumer that reads only our document. A sensor fed the frozen level would report healthy DNS while Blocky is dead — precisely the case the automation exists for. The log does not contradict us: it is silent during inconclusive, so `unknown` fills a gap rather than competing with a claim.
- **It is named for upstream reachability, never for "DNS working".** #326 established the probe's fact is upstream reachability for the `default` group as seen by a local client, and it is deliberately silent when Blocky itself is down. A "DNS working" entity would lie in exactly the case an operator most wants covered, and an entity name is not fixable once it is in someone's automations.
- **The port is published by default and nullable**, following the existing `443/tcp: null` precedent, so an operator who declines a second LAN listener maps it to null and forgoes the sensor. Publishing is required rather than optional: HA core runs on the host network in HA OS — which is why the existing `http://localhost:4000` recipe works — and the internal-hostname route is not viable, since an add-on's Supervisor hostname is `{repo}-{slug}` with a repo hash for a custom repository, so no recipe using it would be copy-pasteable.

**Blocking does not travel with this surface.** Blocking status is already GET-able on `/api/blocking/status`, so for blocking the obligation is already discharged by Blocky itself; re-serving it in our document would invent a second truth that drifts on every Blocky version bump, to save the operator one `rest:` block. Blocking stays on `:4000`, and `DOCS.md` grows from a control-only recipe into **control + observe**.

## Considered & rejected

1. **MQTT discovery — the add-on publishes entities to a broker.** The obvious "real integration" answer, and the one the original question named. Rejected in principle by the direction rule, and #325 priced what the rule avoids. The footprint is genuinely small — the probe loop already exists, the client packages are ≈324 KiB — but the **lifecycle is not**: a one-shot publisher's Last Will never fires, so a stopped add-on reads *available and stale*; honest availability needs the persistent connection the rule forbids, or retained messages the HA docs themselves warn become "ghost entities". Credentials do not come free either — `/services/mqtt` is populated only by an add-on declaring `mqtt:provide`, so an external broker leaves it empty and forces new options onto the curated surface. And on uninstall the Supervisor removes the container, cleans its own records, and never touches the broker: removal falls to the operator by hand. (`mqtt:need` and `mqtt:want` are behaviourally identical — both constants are read nowhere in the Supervisor — so the choice between them was never a real one.)
2. **The Supervisor `discovery:` key.** The ecosystem-native move, and what AdGuard actually does. It is **inert without a companion core integration** to receive it: declaring it alone publishes nothing. It is a complement to a surface, never a surface. Not declared.
3. **A separate HACS or core integration.** The precedent #324 found, and the shape that would give the nicest end-user result. It is a different artifact in a different repo with its own release cycle and its own maintenance — a yardstick for judging this add-on's role, never an answer to "what should *this* add-on do". Out of scope for this effort; if someone builds one, the endpoint above is what it polls.
4. **Do nothing — leave the verdict in the log.** The null comparison, and it is weaker than it sounds. The log carries **edges, not level**: silence is the healthy signal and is indistinguishable from a dead probe, so even a human going looking cannot read current state from it, and an automation certainly cannot. ADR-0012 accepted this explicitly as unsolved rather than fine.

Rejected surfaces *within* the chosen direction, for the record: a `/config` status file and a `/data` status file (not core-readable); a `/share` status file (core-readable, but costs the operator an `allowlist_external_dirs` edit **plus a core restart**, in a flat collision-prone namespace, stretches ADR-0001 — and still reads `healthy` forever after the add-on stops, so making it honest pushes a staleness template onto every consumer); writing into core's `www/` (needs `homeassistant_config:rw`, i.e. write access to the operator's entire HA config directory, and serves the verdict unauthenticated at `/local/…` — a component does not write into another component's directory); and extending Blocky's own API, which #318 established is not available to us.

## Consequences

- **Future "publish X to Home Assistant" requests are answered here.** The direction rule is the first test: if the request needs the add-on to hold an outward connection or own state in another system, the answer is no, and re-opening it takes a new ADR rather than a per-request argument. If the request is only for a fact to be *readable*, the second test applies — is it a Runtime fact that no rendered config can express, and can nothing already-shipped answer it? Blocking failed that second test and stays on Blocky's API; upstream reachability passed it, which is the whole reason a new surface is worth building.
- **`CONTEXT.md` gains `Runtime fact`** and a sentence in the intro paragraph fixing the direction, so the widened domain is stated where the language lives rather than only here.
- **The add-on grows a second listener and a second published port**, which is new surface on both the curated options schema (ADR-0006) and the security story in `DOCS.md`. It is read-only and strictly less exposure than the `:4000` control API already shipping, but it is not nothing, which is why the port is nullable.
- **A machine consumer becomes a compatibility surface.** Entity name, `state` vocabulary and JSON shape are a contract the moment someone writes an automation against them; changing them is a breaking change in the same sense a schema key removal is (ADR-0005). Deriving `state` honestly rather than mirroring the probe is what makes that contract safe to keep.
- **ADR-0012's freeze-on-inconclusive rationale is narrowed, not overturned.** The log still behaves exactly as ADR-0012 specifies; the endpoint diverges only because its reader cannot see Blocky's own errors. Any future consumer of the probe's state inherits the same obligation to derive rather than mirror.
- **No code ships with this ADR.** The implementation is a single follow-up issue carrying the endpoint, the `CONTEXT.md`-adjacent runtime wiring and the `DOCS.md` rewrite into control + observe. It does not re-open the decision.
